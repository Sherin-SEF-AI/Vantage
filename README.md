# Vantage · sensor rig planner for autonomous-driving data collection

A desktop app for designing the sensor rigs of data-collection vehicles, the cars that record the camera data
self-driving models are trained on. Import a 3D model of the vehicle, place the cameras on it, and prove in simulation
what the rig will record before any hardware is fitted: what each camera sees through its real lens model, where the
body blocks it, how many pixels land on the ground and on objects, where cameras overlap, and how sensitive the layout is
to mounting errors and load. Then calibrate the real cameras from their live streams (RTSP/HTTP, V4L2, GStreamer
pipelines such as a Jetson's GMSL cameras), check every installed camera against the plan, and hand the calibration to the
data pipeline (OpenCV, ROS 2, Kalibr, nuScenes, KITTI and more). Lidars and radars sit on the rig next to the
cameras: where their beams and fields reach, what the vehicle blocks, how far they detect each object, how their
timing lines up with the cameras, and how much data the whole rig records.

The same engine also serves production surround-view systems: stitched bird's-eye remap tables, a 3D bowl view, parking
guidelines and where standing people vanish at stitch seams.

**Website and documentation:** <https://sherin-sef-ai.github.io/Vantage/> (feature videos recorded from the app, the full documentation, batch-mode reference). The site's source is `site/`; it is published by `.github/workflows/pages.yml`.

It opens with the **Tata Tigor EV** sample: the body is lofted from the profile measured on the 19-frame studio spin
(wheel-centre calibration, 1.6 px RMS), the cameras are e-con Systems STURDeCAM31 (Sony ISX031, 1920 × 1536, 3.0 µm) with
the H05R2 wide and H03R2 narrow lenses, and five layout variants are included; the fifth, *Data rig*, adds a
128-channel roof lidar and five radars to the six cameras.

The studio photos themselves are not part of the repository. To use the photo-matching features with them, put
`Tata-Tigor-EV-360.zip` in `data/` (or next to the project folder) or set `VANTAGE_TIGOR_PHOTOS` to its path; without
it the sample opens normally with the photo poses but no images.

## Install

**Linux, no Python needed.** Download `Vantage-<version>-linux-x86_64.tar.gz`, then:

```bash
tar xf Vantage-*-linux-x86_64.tar.gz
cd Vantage-*-linux-x86_64
./install.sh            # per user: ~/.local/opt/vantage, a menu entry, the .vantage file type, ~/.local/bin/vantage
vantage --self-test     # checks analysis, OpenCV, fonts, the OpenGL renderer and the main window
```

`~/.local/opt/vantage/uninstall.sh` removes it again (projects and settings are kept). Without installing, run
`./Vantage` from the extracted folder.

**Windows, no Python needed.** Run `Vantage-<version>-windows-x64-setup.exe`. It installs for the current user without
administrator rights, adds a Start menu entry and opens `.vantage` projects. `Vantage.exe` is the window;
`vantage-cli.exe` in the same folder is for batch mode and `--self-test` from a terminal. The `.zip` is the same program
without the installer.

**macOS.** Unzip `Vantage-<version>-macos-arm64.zip` and move `Vantage.app` to Applications. The app is not signed: the
first time, right-click it and choose Open. Batch mode: `Vantage.app/Contents/MacOS/vantage-cli`.

**With Python 3.10 or later:**

```bash
python3 -m pip install .            # from this folder; add [step] for STEP import through gmsh,
                                    # [bags] for compressed ROS 2 bags (zstd, lz4)
vantage                             # the window (vantage-gui on Windows starts it without a console)
vantage --install-desktop           # Linux: Vantage in the app menu and dock with its icon, and .vantage files
vantage --desktop-shortcut          # Linux: the same, plus a Vantage launcher on the desktop
vantage project.vantage --analyse report.json
```

**Building the downloads.** Push a tag (`git tag v1.0.0 && git push origin v1.0.0`) or start *Build installers* in the
repository's Actions tab: GitHub builds and smoke-tests all three and attaches them to the run. To build for the machine
you are on:

```bash
python3 -m pip install -r requirements.txt pyinstaller
python3 packaging/build.py --smoke  # dist/: the bundle, the archive and on Windows the installer (needs Inno Setup 6)
```

## Run

```bash
cd vantage
python3 -m pip install -r requirements.txt     # PyQt6, numpy, scipy, PyOpenGL, PyYAML, opencv-python
python3 run_vantage.py                          # start window
python3 run_vantage.py --sample                 # straight into the Tigor EV sample
python3 run_vantage.py car.glb                  # import a model
python3 run_vantage.py project.vantage          # open a project
```

Options: `--theme dark|light|system`, `--scale 1.15`, `--software-3d` (QPainter 3D view instead of OpenGL),
`--template sedan|hatchback|suv|van|truck|tigor`, `--self-test`, `--version`.

### Batch mode (no window)

```bash
python3 run_vantage.py project.vantage --analyse report.json              # metrics, seams, issues, link budget, targets,
                                                                         # objects in the stitched view + seam advice
python3 run_vantage.py project.vantage --load-cases -                     # load cases as JSON on stdout
python3 run_vantage.py project.vantage --blind-volume volume.json         # 3D blind volume, unseen objects, reach rose
python3 run_vantage.py project.vantage --perception-range ranges.json --variant 2   # detection range per object and
                                                                         # direction, sector verdicts, stereo pairs
python3 run_vantage.py project.vantage --export out/ --formats extrinsics_json,opencv_yaml,bev_lut
python3 run_vantage.py project.vantage --install-check captures/ --report check.json \
        --lut-out out/bev_lut --as-built built.vantage                    # end-of-line check from one image per camera
python3 run_vantage.py project.vantage --calibrate-lens views/ --camera F --board 9x6 --square 60 \
        --serial SN1234 --calib-out F.yaml --save calibrated.vantage      # one camera's own lens, from board views
python3 run_vantage.py project.vantage --import-calib camchain.yaml F.yaml --save calibrated.vantage
python3 run_vantage.py project.vantage --rig-health 10 health.json       # watch every camera's stream for 10 s
python3 run_vantage.py project.vantage --sensor-coverage coverage.json   # lidar/radar reach, blocked beams, verdicts
python3 run_vantage.py project.vantage --sync-plan sync.json             # camera triggers against the lidar sweep
python3 run_vantage.py project.vantage --recording-budget budget.json    # data rate, links, write speed, hours per disk
python3 run_vantage.py project.vantage --power-budget power.json         # loads, DC-DC, fuses, power cables, runtime
python3 run_vantage.py project.vantage --gnss gnss.json                  # antennas' sky, heading baseline, lever arms
python3 run_vantage.py project.vantage --exposure exposure.json          # sun in each camera over a campaign, dirt
python3 run_vantage.py project.vantage --brackets out/                   # a printable STL bracket per camera
python3 run_vantage.py project.vantage --dataset out/                    # a synthetic drive: nuScenes + ROS 2 bag
python3 run_vantage.py project.vantage --drive-log drive/ report/        # a recorded drive against the plan
python3 run_vantage.py project.vantage --fleet-import V3 check.json --fleet fleet/ --save project.vantage
python3 run_vantage.py project.vantage --check review/                   # requirements scorecard + review pack (CI)
python3 run_vantage.py project.vantage --lidar-calib out/ --lidar-calib-pair F L1 --lidar-calib-folder boards/
```

`--variant NAME|N` picks a variant, `--frame`, `--units m|mm` and `--angles deg|rad` set the export conventions, and
`--pos-tol`, `--ang-tol`, `--min-boards` the installation tolerances. The installation check solves all cameras jointly
with the board placement unless `--no-joint`; `--board-tol MM` is how far a board may lie off its planned place
(default 20). The stitched PNG is exposure-balanced unless `--no-balance`, `--blend multiband` for multi-band seams.
`--rig-health SECONDS [OUT.json]` reads the streams set on the Live rig page (saved in the project), waits for their
first frames, then measures for SECONDS and writes `vantage.rig_health/1` (default stdout).
Captures are matched to cameras by tag in the file name (`F.png`, `cam_QR.jpg`, `ML-capture.tif`); imported
calibrations by the camera name or ROS topic in the file, the file name, or the serial number. Exit code: 0 fine, 2 the
plan has critical issues (with `--analyse` or `--export`; with `--recording-budget`, the recorder or a sensor's link
cannot keep up; with `--power-budget`, the DC-DC converter or a fuse is over its rating; with `--gnss`, an antenna has no
sky; with `--brackets`, a camera cannot take a printed bracket as planned), 3 a camera has to be re-mounted or could not
be checked (or, with `--rig-health`, a camera's stream is faulty or not set; with `--drive-log`, the recording shows a
fault; with `--fleet`, a sensor needs re-mounting in its vehicle's latest record; with `--lidar-calib`, the lidar has to be
re-mounted or its pose is not determined), 4 a lens calibration failed or an
imported calibration matched no camera (or did not fit it), or a fleet record, drive log or lidar calibration capture could not be read or the
sample dataset not written, 5 with `--check` a must requirement fails or cannot be evaluated; when several apply, the
highest is returned.

## What is in it

| Area | Features |
|---|---|
| Vehicle import (Ctrl+I) | .glb .gltf .obj .stl .ply .fbx (binary and ASCII), .step via the optional gmsh package. Wizard: units (guessed from the bounding box), up/forward axes and mirroring, inside-out meshes flipped automatically, wheel centres (auto from wheel parts or picked on the mesh), ground plane, origin preset, spec check against datasheet dimensions, occluder simplification, mount zones painted with a brush, glass detected from materials and transparency. |
| Rig (Vehicle ▸ Add rig part) | The data-collection rig on the vehicle as simple solids: **roof rack** (two crossbars and a platform), **sensor mast** (an upright tube with a head 0.5 m above the roof), **sensor enclosure** and **crossbar**, each sized and placed from the vehicle's roof and added as one undo step. Parts are boxes, upright cylinders or bars across the vehicle (centre, size, yaw). A part that *occludes* blocks cameras exactly like the body (ground coverage, blind volume, camera images, the installation check's synthetic captures, the assistant's *why is this point not seen*, which names the part); a *mountable* one carries cameras (place on it, drag along it with surface snapping; a camera on a part that is not mountable is flagged as on a forbidden zone). Listed in the Outliner (select, hide, delete), edited in the Inspector, drawn in 3D and as outlines in the top view, picked with a click; saved with the project and exported as fixed links with box/cylinder geometry in the ROS 2 URDF, a `rig` list in the extrinsics and a table in the report. |
| Lidars, radars, GNSS and IMU (Vehicle ▸ Add lidar / Add radar / Add GNSS antenna / Add IMU) | Lidars and radars on the rig next to the cameras, per variant. The library (nominal figures from public datasheets, each with its source note; check them against your unit's): **Ouster OS1-128** (Rev 7, 128 channels, ±22.5°, 90 m on a 10 % target), **Hesai OT128** (128 ch, −25° to +15°, 200 m), **Hesai AT128** (fixed 120° × 25.4° field, 200 m), **Hesai XT32** (32 ch, 1° spacing, 80 m), **Velodyne VLP-16** (16 ch, ±15°, 100 m), **Livox Mid-360** (non-repetitive 360° × 59°, 40 m, modelled as an even grid with the same points per frame), and three typical 77 GHz radar classes (long-range with a far and a near beam, 4D imaging, corner), which are classes, not products. A lidar goes on top of the highest mountable rig part (a mast head) or the roof, a radar in the middle of the front bumper; then move it in the Inspector (optical centre, yaw/pitch/roll like a camera), drag it in the top view, or pick another model. A lidar is a channel fan (beam elevations, azimuth step, frame rate, range on a 10 % target, points per second, bytes per point, spin direction); a radar is one or more zones (range on a car, ±azimuth, ±elevation), smaller targets reaching the fourth root of their radar cross-section. Editing a built-in model's figures makes an edited copy for that sensor; **Import beam angles…** reads the measured channel elevations from an Ouster metadata JSON, a Hesai angle-correction CSV, a Velodyne ROS calibration YAML or a plain list. Drawn in 3D (housing; the lidar's ground rings, where its downward beams meet the ground; the radar's field edges) and in the top view (rings, radar fields, footprints, tags), picked with a click, listed in the Outliner (select, hide, delete). The Issues list flags a lidar inside the body or a rig part, a radar deeper than 15 cm behind the bumper surface, a sensor below the ground and a tag a camera also uses. Saved with the variant; exported as frames (x forward, y left, z up at the optical centre) in the extrinsics (with the field and spin), the ROS 2 URDF (links with the housing) and static TF launch file, the nuScenes `sensor` / `calibrated_sensor` tables (`LIDAR_<TAG>`, `RADAR_<TAG>`), KITTI (`Tr_<tag>_to_vehicle`, and `calib_velo_to_cam.txt` for the first lidar into camera 00) and the report. **GNSS antennas and IMUs** sit on the rig the same way: an antenna's position is its phase centre (a typical survey antenna and a compact patch antenna in the library), an IMU's the centre of its axes and its frame its own axes (typical dual-antenna MEMS GNSS/INS, FOG GNSS/INS and MEMS IMU classes, with heading error at a stated baseline, RTK position error, roll and pitch error, output rate, antenna inputs; not products: enter your unit's figures). The first antenna goes near the rear edge of the roof (or the rack over it), the second near the front edge for the longest heading baseline, the IMU on the cabin floor above the rear axle; the Inspector shows each antenna's baseline and the INS's heading error for it, the 3D and top views draw the baseline and the IMU's axes. The Issues list flags an antenna inside the body or a rig part (no sky); an IMU belongs inside. They are exported in the extrinsics, the URDF and TF, KITTI (`Tr_<tag>_to_vehicle`, and `calib_imu_to_velo.txt` from the first IMU into the first lidar) and the report; nuScenes has no GNSS or IMU channels (they make its `ego_pose`). The recording budget counts an INS's output. |
| Camera modules | Library of modules and lenses; module editor with datasheet fields, projection models (rectilinear, equidistant, equisolid, stereographic, measured Kannala–Brandt), a live r(θ) plot, distortion table, image circle on the sensor, derived values and datasheet-vs-model FOV check. Import from JSON, CSV or OpenCV YAML. |
| Placement | Place on surface (C, Alt-click for a mirrored pair), drag from the library, move handles (G: an arrow per axis and a square for the horizontal plane) and rotate rings (R) on the selected camera, sensor or rig part (a rig part turns about z), lit under the pointer, with the change read out beside the cursor while dragging (Ctrl snaps to 1 cm / 5°, Shift is fine, Esc puts it back with no undo step); drag a selected sensor or rig part itself across at its height, drag along the body with surface snapping, aim at a ground point (Camera ▸ Aim ▸ At ground point, then click in 3D or the top view), linked L/R pairs, scrubbable number fields that accept expressions and units, editable camera spreadsheet with paste from Excel, coordinate frames (rear axle, front axle, front bumper, centre, custom) in m or mm. |
| Analysis | Live, incremental ground coverage on a 5/2/1 cm grid inside an ROI (true offset or polygon): blind area, redundancy, best-camera pixel density, focus, per-camera unique/overlap areas, "if removed" figures, stitch seams, worst single-camera error, obstacle poles and vertical targets. Body occlusion is exact per camera (cube depth maps). |
| Views | 3D (OpenGL, QPainter fallback), top coverage/density/redundancy maps (density drawn smooth on a colour-blind-safe blue scale that starts at the project's minimum, ground below the minimum grey and hatched, iso-lines at the minimum and target density; redundancy in three ordered steps; best camera in crisp cells; blind ground red and hatched; a legend for every mode in the corner that hides the least; a hover read-out with a crosshair: the value under the cursor, its state against the thresholds and every camera that sees the point with its px/cm, range and off-axis angle; hovering a camera's bar in the Coverage panel lights up the ground only it sees), charts with exact-value tooltips and labelled thresholds, simulated fisheye camera images, stitched bird's-eye with draggable seams, bowl view, 1/2/4 viewport layouts, photo-matched shading (the active 3D view looks through a calibrated reference photo with the model drawn translucent over it; [ and ] step through the photos). |
| 3D rendering | Shader renderer (GLSL 1.20, falls back to fixed-function GL, then to QPainter): geometry kept on the GPU, smooth normals with crease angles, lighting in linear space with a gentle highlight roll-off (data colours such as heatmaps and camera light keep their exact legend colours), materials from the mesh's parts and zones (clear-coated paint reflecting a studio environment, dark see-through glass, matte tyres, black trim, light lenses, rig metal), sky occlusion that darkens wheel arches, mirrors and where sensors and rig parts meet the roof (rebuilt only when the geometry changes), soft Poisson-filtered shadows that the body, the rig and every sensor housing cast on the ground and on each other, a smooth contact shadow under the body, a studio backdrop on the real horizon (flat for top views, photos and the bowl), MSAA. Sensors and cameras are drawn at their real size and pose: a lidar with its window band, a radar with its radome, a GNSS antenna as a dome, an IMU with its axes, each camera module with a lens ring in its colour; the selected one gets an outline. Overlays: radar zones as see-through volumes fading out to 15 m; **Lidar points** (one simulated sweep per lidar, computed in the background: returns coloured by range, beams the body, the rig or another housing stops in red — on the sample 36 % of the roof lidar's beams); **GNSS sky** (a dome over each antenna coloured where the GNSS study finds the sky blocked, with its open share); **Mount brackets** (generated brackets on the vehicle in their camera's colour). The QPainter fallback draws the same points, outlines and overlays in a simpler form. **Camera light** (View ▸ Overlays, Alt+3): every camera's real lens model and body occlusion evaluated per pixel, so the body and the ground show what each camera sees (overlaps hatched) live while a camera is dragged; the software renderer computes the same on the CPU. Animated view changes; **Render image…** (Ctrl+Shift+R, up to 4× the view size, vector overlays stay crisp) and **Turntable video…** (MP4 with ffmpeg, else PNG frames). |
| 3D navigation | Orbit about the point under the cursor where the drag starts (the body, a rig part, a sensor, a camera or the ground; a dot marks it), so what you grab stays put; the wheel zooms towards the surface under the cursor. A navigation control in each 3D view's top-right corner for any mouse or touchpad: drag the axis ball to orbit, click an axis to look along it, drag the hand to pan or the magnifier to zoom, frame everything, switch perspective and orthographic. Touchpad: two fingers orbit, Shift + two fingers pan, pinch or Ctrl + two fingers zoom. Keyboard (3D view focused): arrows orbit (Alt for small steps), Shift + arrows pan, + and − zoom, 7 / 1 / Ctrl+1 / 3 top, front, rear and side on the number row or the numpad, 0 the default view, 5 orthographic. Preferences ▸ 3D navigation picks Blender-style (middle-drag orbits) or CAD-style (right-drag orbits) mouse buttons; left-drag on empty space always orbits. |
| 3D surround view (Camera views ▸ bowl) | The view an in-car display shows: camera images projected through each lens onto a bowl around the car (flat floor, curved wall; floor, wall height, reach, profile and squareness are tunable and saved with the project) with the seams, exposure balancing and blending of the bird's-eye view, and the car model in the middle; typical display viewpoints. Images come from a synthetic parking scene rendered through every camera (bay markings, parked cars, a pillar, a bollard, the project's obstacles, a garage wall), from the installation check's captures, or just the camera sectors. Export the bowl as OBJ + texture with per-vertex remap tables (sensor pixel and weight per camera) for an ECU renderer. |
| Parking guidelines (Camera ▸ Parking guidelines…; Camera views ▸ steering bar; View ▸ Overlays ▸ Parking guidelines, Alt+G) | What a surround-view display draws while parking, from a kinematic bicycle model of the vehicle (wheelbase and track from the wheel centres, body width without the mirrors from the mesh): static width lines and distance markers, the trajectory of the bumper corners for the steering angle with red / yellow / green distance bands and ticks, and the **swept path** of the whole body with its mirrors. Reverse or forward; a steering slider (left of centre steers left; the views follow while dragging, one undo step per drag) shows the road-wheel and steering-wheel angle and turning radius. Drawn through each camera's real lens (fisheye curvature, image circle, body occlusion, unit calibrations) over the camera images, on the bird's-eye view, in the bowl, and on the ground in the 3D and top views; obstacles inside the swept path are flagged with the distance at which the body (or, for tall ones, a mirror) would touch them. Export per camera for the ECU: a JSON table of pixel polylines with colours and labels for every steering angle from full lock left to full lock right (sensor pixel convention as the remap tables), the ground polylines in the export frame, and a PNG preview over the synthetic parking scene. |
| Studies | Monte Carlo tolerance study with sensitivity tornado and pinned worst cases; evolutionary placement optimiser scored under tolerance with a Pareto front; side-by-side variant comparison with Δ density map; calibration target planner with auto-place and suggestions; reference-photo matching (spin scrubber, landmarks, OpenCV calibration, matched 3D view). |
| Installation check (Calibrate ▸ Installation check…, Ctrl+Shift+I) | One image per camera from a file, a live stream (V4L2 device, GStreamer pipeline, RTSP/HTTP URL; preview and grab) or a synthetic capture rendered from the plan with an optional simulated mounting error. The floor boards are cut out of each fisheye image as rectified pinhole patches (exact lens model), the chessboard corners found with OpenCV, and the installed pose solved by PnP on the bearing rays; boards that do not agree with the rest are dropped and the detection is repeated around the solved pose. Per camera: boards, corners, RMS, Δx Δy Δz, Δψ Δθ Δφ and a verdict against the tolerance (OK / adjust / re-mount). The captures are stitched into the bird's-eye view with the planned and with the measured poses side by side; save the report, the PNG, the remap tables, or apply the measured poses as an *as-built* variant. |
| Live rig health (Calibrate ▸ Live rig…) | Every camera's stream at once, for the rig on the vehicle before a collection drive. Each camera's source is saved with the project and shared with the installation check's live field: an RTSP/HTTP URL, a V4L2 device, a GStreamer pipeline, a video file, or *Synthetic* (the parking scene rendered through the camera's lens at the module's frame rate, or one typed in, with sensor noise; a stand-in until the hardware is fitted). A password in a stream URL is not saved in the project: it goes to `stream-credentials.json` in the settings folder (readable only by you, keyed by user@host:port) and is put back when the stream is opened, so a shared project carries no camera passwords; labels, the history and reports show it as `***`. Per camera, from frame arrival times and the images: measured frame rate against the module's, interval jitter, dropped frames (gaps over 1.5 frame intervals), age of the newest frame, resolution against the module's sensor, mean brightness, clipped share, sharpness (variance of the Laplacian, for a blurred, fogged or covered lens) and frozen images, with an OK / warning / fault verdict and its reasons; for the rig the cameras up, the worst frame rate, faults and the sync skew between cameras (from software timestamps: when frames reached Vantage, not sensor time). Over each image the planned body outline and horizon through the lens model, and an edge alignment indicator (median distance of the planned body edge to the edge in the image) that flags a camera that may have moved; an indicator, not a measurement. Readers run on their own threads and reconnect with back-off (1, 2, 4 … 15 s); the page stops them when hidden. **Save frames** writes `<tag>.png` per camera and `rig_health.json`; **Check installation** hands the frames to the installation check. All thresholds are in `HealthSettings` (`vantage/core/rig_health.py`). |
| Unit lens calibration (Calibrate ▸ Lens calibration…, Ctrl+Shift+L) | Every camera can carry its own intrinsics instead of the library lens: calibrate from 10–20 views of a hand-held checkerboard (image files, a live stream, or a synthetic set rendered through a simulated unit), fitted as cv::fisheye (Kannala–Brandt, fx/fy/cx/cy/k1–k4). Boards the raw fisheye distorts too much are found in rectified views and mapped back exactly; poor views are dropped. Shows per-view RMS, corner coverage over the image with advice, parameters against the library lens, and how far the library lens would put a ray on this unit. Import calibrations made elsewhere (OpenCV YAML/XML, ROS camera_info, Kalibr camchain, JSON), matched to cameras by name, topic, file name or serial. The unit calibration replaces the library lens in the analysis, the installation check, the remap tables and every export (which says so). |
| Joint extrinsic solve | The installation check refines all cameras together with each board's placement on the floor (x, y, yaw under a placement prior) in one sparse least-squares problem, so cameras that share a board agree at the seams even when the boards were laid a centimetre or two off. It reports the seam agreement before and after (floor disagreement of corners seen by two cameras), the estimated board positions, names boards that lie beyond their tolerance, and sets aside a board observation no placement explains. |
| Lidar–camera calibration (Calibrate ▸ Lidar–camera calibration…) | Where a lidar sits relative to a camera, and so in the vehicle, measured from a printed checkerboard held up at several poses both see, against the plan. The pair is ranked by how much of the camera's image the lidar's beams cover. The **pose plan** places each board where both sensors see all of it, at least four lidar channels cross it and its squares stay big enough in the image, turned (yaw, pitch, roll) for what its plane adds to pinning the lidar's six degrees of freedom, and shows the uncertainty the plan can reach. Captures are **synthetic** (the camera image through its real lens, the lidar scan with the model's beams and range noise, with an optional injected mounting error to see the recovery) or a **folder** of real image + point-cloud pairs (PCD, KITTI .bin, nuScenes .pcd.bin, PLY, .npy, CSV). The camera finds the corners through the exact lens model; the lidar gives the board plane, its edge (bracketed between the last beam on the board and the first beam past it) and, when its reflectivity shows them, the squares. One robust solve of the extrinsic and every board's pose gives T_camera_lidar with its 1σ, Δ against the plan in the camera and vehicle frames, a verdict against the tolerances, a moved board set aside, and a set of boards that cannot pin a direction named as such ("the boards were all tilted the same way: the translation along z is not determined"). The lidar's points drawn on the image through the plan and the solved extrinsic are the visual proof. Apply the measured pose to the lidar (one undo step) or as a new variant; export JSON (both directions, matrix and quaternion, covariance) and an overlay PNG per pose. |
| Drive-log check (Calibrate ▸ Drive-log check…) | Checks a recorded drive (a ROS 2 bag or a nuScenes folder) against the plan. **Streams**: every stream is there, at its rate, with no drops, sane latency and the right image size. **Data rate**: what each sensor recorded against the recording budget, including real compression. **Sync**: are the cameras triggered in step with the lidar sweep as the sync plan says (the lidar's measured phase lock, and each camera's own trigger error). **Rotations**: do the lidar points land on the right pixels; each camera's rotation is found relative to the lidar from depth edges against image edges, with a confidence. **GNSS/IMU**: gravity and gyro bias at rest, fix shares. Then apply the confident rotations as a corrected variant. |
| Fleet (Calibrate ▸ Fleet…) | The same rig built on many vehicles and calibrated again over months. Each vehicle (name, VIN, note) collects records: the measured poses of its sensors on a date, imported from an installation check report, Vantage's extrinsics JSON/YAML/CSV (converted back from their export frame, mm/m and deg/rad), nuScenes `calibrated_sensor.json` + `sensor.json` (optical camera frames converted back; the ego origin from the README beside them), a Kalibr camchain (camera-to-camera only, so it is placed on the plan by the best rigid fit), a variant of the project, or typed in; tags match the plan ignoring case, and unknown ones are reported. Against the plan (a chosen variant): per vehicle and sensor the latest Δx Δy Δz and Δyaw Δpitch Δroll and a verdict like the installation check's (ok, adjust, re-mount). Over time: a least-squares trend per 30 days (a component counts when it is significant in a t-test), the days until it leaves the tolerance, and a flag when that falls within the drift window or when the latest step jumps off the earlier course. Across the fleet: the median per sensor and a robust z-score per vehicle ("V4: ML is yawed 2.0° left of the fleet median"); when most vehicles share an offset beyond tolerance, the plan is wrong, and **Variant from the fleet median** makes the as-built plan in one undo step.
